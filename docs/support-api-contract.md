# Support API contract

Decision record for [issue #6](https://github.com/Quick-Release/gq-support/issues/6). It specifies the browser → WordPress REST contract and the WordPress → Worker transport adapter. [ADR 0009](adr/0009-project-repository-intake-and-reporter-scoped-projection.md) limits the surface to issue intake and a Reporter-scoped projection, and the [support security design](support-security-design.md) owns the authentication and authorization rules this contract relies on. [CONTEXT.md](../CONTEXT.md) defines the terms. This is a contract, not a claim that it is implemented.

The [Report context decision](support-context-design.md) extends create with reviewed, removable default context, a server-authenticated review envelope, frozen context in the idempotent intent, and matching PHP/Worker fixtures. [#71](https://github.com/Quick-Release/gq-support/issues/71) implements it as described below and in that decision. It keeps the three REST routes and the 32 KB body cap. Rich technical details are deferred beyond the MVP.

## Routes

Namespace: `gq-support/v1`. The namespace is the version, and responses carry no separate version field. Routes are registered on `rest_api_init`, always, including on an unconfigured installation.

| Method and path | Capability | Purpose |
|---|---|---|
| `POST /requests` | `gq_support_submit_requests` | Create one Support request (idempotent per Submission ID) |
| `GET /requests?scope=mine` | `gq_support_submit_requests` | List own requests (default scope) |
| `GET /requests?scope=site` | `gq_support_view_site_requests` | List every request from this installation; the same grant closes or reopens them (ADR 0020) |
| `GET /requests/{id}` | own: submit; other's: view-site | Read one request |
| `POST /requests/{id}/status` | own: submit; other's: view-site | Close or reopen one delivered request (idempotent per Change ID; [ADR 0020](adr/0020-reporter-status-changes-are-ordered-intents.md)) |

WordPress privacy tools reach the Worker without a REST route: the personal data exporter and eraser, and the deleted-user hook, call signed `GET /v1/export`, `POST /v1/erasures` and `GET /v1/erasures/{id}` directly ([privacy design](support-privacy-design.md#worker-contract)).

Every other path returns 404. There are no receipt, message, reply, or attachment routes. Delivery outcome is a field on the request resource. Adding any of these routes needs a new decision (ADR 0009); close/reopen was added by [ADR 0020](adr/0020-reporter-status-changes-are-ordered-intents.md) (#28).

Every route has a `permission_callback` that checks the cookie session, the `wp_rest` nonce, current site membership, and the capability. Object access is checked again at the Worker for the installation plus either the attested Reporter subject or a freshly attested view-site grant. An unknown request, and a request outside the caller's scope, both return **404**, so the response never reveals that the request exists. `scope=site` never means cross-installation.

## Request and resource shapes

### Create

```http
POST /wp-json/gq-support/v1/requests
X-WP-Nonce: <wp_rest nonce>
Content-Type: application/json

{
  "submission_id": "3f0c2a4e-6b1d-4c1e-9a55-0d8e3f2b7c11",
  "summary": "Checkout button does nothing",
  "description": "On the cart page, clicking Checkout does nothing. I expected the payment step."
}
```

| Field | Rule |
|---|---|
| `submission_id` | Required UUIDv4, generated by the browser per draft and reused for every retry of that draft. |
| `summary` | Optional. One line, 1–120 characters after trimming. |
| `description` | Required. 1–10,000 characters after trimming. |
| `supersedes_id` | Optional public request identity, only when replacing a failed own request. It must belong to the same Slot and Reporter. |
| `context` | Optional, only with `context_review`: `{"schema": 1, "default": {…}}` holding the reviewed values the Reporter kept, among `wp_version`, `support_plugin_version` and `originating_screen` ([context design](support-context-design.md#implementation-of-the-minimal-context-71)). Unknown keys or sections and malformed values are rejected. |
| `context_review` | Required with `context`: the review envelope the context preview issued for this Submission ID. WordPress verifies it and never forwards it. |
| anything else | Rejected (`additionalProperties: false`). There is no category or attachment field in v1. Environment is added by the service from the Repository mapping. |

The whole request body, including any context and envelope, is capped at 32 KB. Limits live in one constants file per side, and shared fixtures assert they agree.

The context preview is the authenticated, read-only `admin-ajax.php` action `gq_support_context`, not a REST route. It answers `private, no-store` with the default context and its envelope, checks the same session, nonce, membership and capability as the routes, and never calls the service.

The Submission ID is a reference, not authority. The Worker scopes it to (installation, Reporter subject), so the same UUID from another Reporter is a different key.

### Resource

```json
{
  "id": "req_01J8Z6Q4M1ZC7",
  "submission_id": "3f0c2a4e-6b1d-4c1e-9a55-0d8e3f2b7c11",
  "title": "Checkout button does nothing",
  "summary": "Checkout button does nothing",
  "description": "On the cart page, clicking Checkout does nothing. I expected the payment step.",
  "created_at": "2026-09-28T10:00:00Z",
  "delivery": "delivered",
  "status": "open",
  "status_change": null,
  "own": true
}
```

- `id` is an opaque service-issued identifier. It is never a GitHub issue number, URL, or repository name.
- `title` is `summary`, or the description's first line cut at a word boundary to about 80 characters.
- `delivery` is one of `accepted-pending`, `delivered`, `failed`, or `outcome-unknown`. `locally-unsent` is a browser-only state and never goes over the wire.
- `status` is `open` or `closed` once `delivered`, and `null` before that. GitHub is authoritative (ADR 0003).
- `status_change` is the latest close or reopen, or `null` when there has been none: `{ "change_id": "<UUIDv4>", "status": "open|closed", "delivery": "accepted-pending|delivered|failed|outcome-unknown" }`. Its `delivery` is the change's own outcome and never replaces `status`, which stays GitHub's. An older service that sends no `status_change` is read as `null`.
- `own` is `true` when the request belongs to the current Reporter. WordPress sets it after verifying the service's ownership metadata (below); the Worker never sends it, and any value it sends is discarded. It identifies no Reporter. The widget marks own requests only in `scope=site`, where a Support manager sees other Reporters' requests too.
- Timestamps are UTC ISO 8601. The browser formats them in the site timezone.
- Text is plain and is escaped when rendered. There are no comments, labels, assignees, or repository fields.

### List

`GET /requests?scope=mine&per_page=20&cursor=<opaque>` returns `{ "items": [Resource…], "next_cursor": "<opaque>|null" }`, newest first. `per_page` defaults to 20 with a maximum of 50. There are no totals and no `X-WP-Total`. A cursor is opaque and valid only for the same scope and caller.

## Create semantics

| Outcome | Response | Reporter sees (see domain design) |
|---|---|---|
| Same-key replay of an already delivered request | `201` + `Location`, `delivery: delivered` | "Open" |
| Intent durably recorded, not yet delivered | `202`, `delivery: accepted-pending` | "Received" |
| Repeat of a known Submission ID with the same body | The existing resource with its current code (`201`/`202`), and no second issue | per `delivery` |
| Same Submission ID, different body | `409 gq_support_idempotency_conflict` | "Not sent", and the draft gets a new key |
| Worker could not durably record | `503 gq_support_not_accepted` (retryable) | "Not sent" + Try again with the **same** key |
| Timeout or unparseable/ambiguous Worker response | `504 gq_support_outcome_unknown`, echoing `submission_id` | "Checking…" |
| An accepted intent later fails terminally | the resource with `delivery: failed` | "Not sent" + Try again with a **new** key |

Rules:

- A retry after a known failed delivery uses a new Submission ID and `supersedes_id` naming that failed request. Acceptance atomically hides the predecessor from lists; it remains readable by its owner. Missing, out-of-scope, already replaced, and non-failed targets all return the same sanitized 404. Same-key reconciliation includes the frozen predecessor reference; changing or removing it returns 409.
- Success is never inferred from `blocking => false`, from a transport return without a parseable body, or from a 2xx without a valid resource.
- **Re-POSTing with the same Submission ID is the reconciliation path for ambiguous transport completion.** The Worker either finds the existing intent or creates it exactly once. "Checking…" retries the same key and frozen payload automatically, at most 3 times with 1/2/4-second minimum backoff (respecting `Retry-After`) and only while the panel is open, and then offers a "Check again" button. Closing/reopening, focus and visibility changes never reset that budget. It never sends the report as a new issue (ADR 0003, ADR 0006).
- [The delivery decision](support-delivery-design.md) selects durable intake: new requests return `202` immediately after the atomic D1 acceptance. Delivery happens in background; a same-key replay returns `201` if already delivered and `202` for other recorded outcomes, with the current `delivery` field. A known resource with `delivery: outcome-unknown` is distinct from an ambiguous transport response (`504`).
- A valid `outcome-unknown` resource ends acceptance reconciliation: show "Delivery needs review" and use manual GET refresh for that resource. Never offer a new creation intent for it. A later rejection of a reconciliation attempt (including 409) does not prove an earlier uncertain attempt failed. Preserve the original key and frozen payload and require safe reconciliation or Operator review before any replacement; the ordinary new-key conflict rule above applies only once prior ambiguity is resolved. See the [outage and draft-recovery decision](research/outage-draft-recovery.md) for navigation loss, authentication boundaries and recovery tests.

### Status change

```http
POST /wp-json/gq-support/v1/requests/req_01J8Z6Q4M1ZC7/status
X-WP-Nonce: <wp_rest nonce>
Content-Type: application/json

{ "change_id": "7d2c6f1e-3b4a-4c5d-8e9f-0a1b2c3d4e5f", "status": "closed" }
```

The body is exactly a browser-generated UUIDv4 `change_id`, new for each action and reused only to check an uncertain one again, and the requested `status`, `open` or `closed`. Anything else is rejected with 400 (`status-change.json`). WordPress forwards it to the signed `POST /v1/requests/{id}/status` with the attested `reporter_subject` and a `scope` of `site` when a fresh view-site grant is present, otherwise `mine`. The Worker scopes the Change ID to the request.

| Outcome | Response | Reporter sees |
|---|---|---|
| Newly accepted | `202`, the resource with `status_change.delivery: accepted-pending`; `status` unchanged | "Close requested. Delivery is pending." beside the GitHub badge |
| Same Change ID and status again | The resource with that change: `200` once delivered, otherwise `202` | per its `delivery` |
| Same Change ID, other status | `409 gq_support_idempotency_conflict` | Try again, with a new key |
| Create not yet delivered, or issue lost | `409 gq_support_change_not_allowed` | "can't be changed yet" |
| An earlier change is pending or unknown | `409 gq_support_change_pending` | "still being delivered. Refresh to see it." |
| Unknown or out-of-scope request | `404 gq_support_not_found` | "no longer available" |
| Worker could not record it | `503 gq_support_not_accepted` (retryable) | Check again with the **same** key |
| Timeout or unparseable/ambiguous reply | `504 gq_support_outcome_unknown`, echoing `change_id` | "We couldn't confirm this status change." + Check again with the same key |

A reply counts only if it names the sent Change ID and status, with `200` exactly when that change is delivered. The widget offers Close or Reopen only on a delivered request whose latest change is delivered or failed. It never resends on its own, and never after reauthentication. Delivery, reconciliation before any resend, ordering and quotas are in [ADR 0020](adr/0020-reporter-status-changes-are-ordered-intents.md).

## Error catalogue

Every error is a `WP_Error` whose `data` is `{ status, correlation_id, retryable }`. Errors never include the upstream body, the Worker URL, exception text, credentials, or report content.

| HTTP | Code | When | Reporter sees |
|---|---|---|---|
| 401 | core `rest_not_logged_in` / `rest_cookie_invalid_nonce` | Session or nonce expired | "Your session expired. Reload the page to continue." Draft kept |
| 403 | `gq_support_forbidden` | Missing capability or site membership | Same as 401 |
| 400 | core `rest_invalid_param` / `gq_support_invalid_request` | Schema or limit failure | Inline field error |
| 413 | `gq_support_payload_too_large` | Body over 32 KB | Inline error |
| 404 | `gq_support_not_found` | Unknown or out-of-scope request | "Not found" |
| 409 | `gq_support_idempotency_conflict` | Same key, different body | "Not sent", new key on retry |
| 409 | `gq_support_change_not_allowed` | Status change: the create is not delivered, or its issue was lost | "This request's status can't be changed yet." |
| 409 | `gq_support_change_pending` | Status change: an earlier change is unresolved | "An earlier status change … is still being delivered." |
| 412 | `gq_support_context_expired` | Create: the review envelope expired and the service holds no intent for this Submission ID | The panel reviews the context again for the same Submission ID; if an earlier send is uncertain, "Check My requests" |
| 426 | `gq_support_plugin_outdated` | Create or status change: the release policy refuses this plugin version new intake (#141), or WordPress's cached policy already did. An accepted intent or change still replays first | "Support needs a plugin update" |
| 429 | `gq_support_rate_limited` + `Retry-After` | Per-subject or per-installation limit | "Too many requests, try again later" |
| 503 | `gq_support_not_configured` | No connection, or the Worker rejected the installation credential | "Support is unavailable"; operator sees detail on the setup page |
| 503 | `gq_support_disabled` | `GQ_SUPPORT_DISABLED` is set in `wp-config.php`; checked after authorization, before any service call | "Support is temporarily disabled" + independent contact; `retryable: false` |
| 503 | `gq_support_not_accepted` | Create or status change: the Worker could not durably record | "Not sent" + Try again (same key) |
| 503 | `gq_support_unavailable` | Read: Worker down, timed out, or ambiguous | "Couldn't load. Refresh to try again." |
| 504 | `gq_support_outcome_unknown` | Create or status change: timeout or ambiguous response | "Checking…" |
| 500 | `gq_support_internal` | Anything else | Generic error with correlation ID |

- A Worker authentication or signature failure is **never** returned to the browser as 401/403. That would look like an expired session and send the Reporter into a reload loop. It maps to `503 gq_support_not_configured`.
- Automatic retries follow `Retry-After`. A 429 is never retried automatically, and a write is never replayed after reauthentication (security design, test group 6).
- The status matrix covers auth expiry (401/403), rate limits (429), GitHub unavailability (`202 accepted-pending` if the intent is durable, otherwise `503 gq_support_not_accepted`), and ambiguous write completion (`504` plus same-key reconciliation).

## Caching

Every `gq-support/v1` response sends `Cache-Control: private, no-store` explicitly, rather than relying on core's logged-in no-cache default. WordPress keeps no transient or object cache of projections in the MVP, so every list and read goes to the Worker. Reads only happen when My requests is shown or refreshed.

## WordPress → Worker transport

`GQ_Support_Service_Client` is the one adapter. It uses WordPress's HTTP API and has no third-party HTTP client.

| Concern | Policy |
|---|---|
| Destination | Base URL is a plugin constant, overridable only by `GQ_SUPPORT_SERVICE_URL` in `wp-config.php` (staging, dev). It is not an admin-editable option, so a site admin cannot redirect signed traffic. HTTPS only. |
| Function | `wp_safe_remote_request()` (`reject_unsafe_urls`) |
| Redirects | `redirection => 0`. A 3xx is treated as an ambiguous response. |
| TLS | `sslverify => true` |
| Timeouts | 8 s for create and status changes, 5 s for reads. The browser's `apiFetch` timeout is about 15 s. |
| Response size | `limit_response_size` 64 KB. An oversized or unparseable response is ambiguous. |
| Worker path | `/v1/...`. The path version changes only on a breaking change, and `/v2` then runs alongside `/v1` until the fleet has migrated. |
| Version header | `GQ-Support-Plugin-Version`, signed (below). Within v1 the Worker makes only additive changes. New intake follows the [release policy](#release-policy): other versions get 426. |
| Signing headers | `GQ-Support-Key-Id`, `GQ-Support-Installation-Id`, `GQ-Support-Plugin-Version`, `GQ-Support-Timestamp`, `GQ-Support-Request-Id`, `Content-Digest` (RFC 9530, sha-256), `GQ-Support-Signature`. The signer is an injected dependency. Ed25519 over the `gq-support-v2` canonical string, which includes the plugin version after the installation ID; a five-minute clock window and single-use request IDs, as implemented in the [security design](support-security-design.md#implemented-installation-authentication-32). The Worker still verifies legacy `gq-support-v1` signatures, whose version header is unsigned and therefore ignored: the version is unknown. |
| Forwarded identity | The attested Reporter subject and, for `scope=site`, a freshly attested view-site grant. There is no WordPress nonce, cookie, email, username, or numeric user ID, and no browser-supplied installation, Client, or repository. |
| When calls happen | Only inside a `gq-support/v1` route callback. Never during page rendering, activation, or cron. |

WordPress → Worker payloads carry the same field names and limits as the browser contract, plus the attested identity, as compact unescaped JSON. Report context travels without its review envelope; an expired envelope adds `reconcile_only: true`, which only returns an already accepted intent (or 412) and never accepts one. The service caps a create carrying context at 32 KB.

## Release policy

Implements [ADR 0021](adr/0021-automatic-fleet-updates-with-latest-version-support.md) for #141 (`worker/src/release-policy.ts`, `plugin/includes/class-gq-support-release.php`).

- The service accepts a new create or status change only from the approved release's signed version, or from the previous approved release until 24 hours after the approved release's recorded fleet dispatch (until its dispatch is recorded, without limit). A legacy `gq-support-v1` request counts only as an approved release recorded as an unsigned legacy package. An approved release outside the Worker's supported contract versions takes no intake.
- The check runs after the same-key lookup: a retry of an accepted Submission ID or Change ID returns its receipt, never 426. Reads, lists, export, erasures, self-revocation and `GET /v1/installation` are never gated.
- A refused version gets `426 {"code": "gq_support_plugin_outdated", "release": {…}}`. When enforcement is unconfigured, nothing is approved or a record is malformed, new intake gets `503 gq_support_not_accepted` instead: a service fault no plugin update fixes.
- `GET /v1/installation` adds `release`: `{enforcement: "enforced"|"staged"|"unconfigured", intake: "open"|"closed", reason: "current"|"previous"|"unsupported"|"expired"|"unavailable", plugin_version, approved_version, compatible_until}`, or `null` when storage could not say. `compatible_until` is set only while an enforced previous release's window runs. A `staged` stage reports the evaluation but keeps intake open.
- WordPress caches a well-formed `release` for its own version from the setup page's connection test and from a 426. With no remote call it closes new reports when the cached policy is `unsupported` or `expired`, or once `compatible_until` passes; it is `unknown` before the first answer and after the plugin itself is updated. A locally closed create is forwarded with `reconcile_only: true`: an accepted intent is returned, otherwise WordPress answers 426. Status changes, reads and `GQ_SUPPORT_DISABLED` behave as before; the service gates status changes.

## Contract tests

Shared JSON fixtures in `contract/fixtures/` are the drift guard. There is no generated shared schema, because the two hops are different shapes and WordPress REST supports only a subset of JSON Schema. PHPUnit and the Worker test suite both run every fixture.

- Valid and invalid create payloads, covering each limit boundary, unknown fields, a missing or malformed `submission_id`, and multi-line summaries.
- Valid and invalid Report context, with its canonical serialization (`context.json`).
- Resource and list responses for each `delivery`/`status` combination.
- Signed and legacy signing strings (`signing.json`), version mismatch (426) and every error code in the catalogue.

The adapter is tested with `pre_http_request` stubs for 2xx, each Worker error, timeout, 3xx, oversized body, malformed JSON, and TLS failure. Each case checks the mapped browser error and that no secret or report content reaches the logs.

## Acceptance for implementation

- Each route in the table exists with a `permission_callback` and argument schema, and every other `gq-support/v1` path returns 404.
- Out-of-scope and unknown IDs return the same 404.
- Create is idempotent per (installation, subject, Submission ID). A conflicting body returns 409. A timeout returns 504, and a same-key retry never produces a second issue.
- The error catalogue, `Cache-Control: private, no-store`, and the transport policy are verified by tests.
- No external calls during unrelated page rendering or plugin activation.

## WordPress authorization implementation (#31)

The WordPress routes use the logged-in cookie and `X-WP-Nonce` together; application passwords or a programmatically selected current user alone cannot authorize them. In multisite, an actual site role/user grant and site membership are required, including for network Super Admins. Initial Administrator grants and uninstall ownership remain governed by the existing versioned per-site lifecycle.

The service request attests `reporter_subject` and `scope` (`mine` or `site`). Creates put these fields in the signed JSON body; reads put them in the signed query string alongside the validated pagination fields. The browser cannot supply either field. The installation identity remains in the signing headers, and the service must resolve its approved Slot and repository from that credential. Subjects are random UUIDs stored in site-prefixed user metadata, partitioned by local installation identity; account deletion removes them and a replacement account receives a new subject. First use is serialized by a connection-owned MySQL/MariaDB named lock with a one-second wait; WordPress rereads metadata under the lock and fails closed if initialization fails.

Each service resource also returns `installation_id` and `reporter_subject` as server-only ownership metadata. WordPress verifies both for own reads and creates, and the installation for explicitly granted site reads, before stripping the metadata and returning the public resource fields plus `own`. Lists check every item. Unknown and mismatched resources produce the same 404. This is defense in depth: the Worker must independently authorize before returning any resource. Its route implementation and verifier belong to the service work; these WordPress integration tests stub that external boundary.

The deferred widget uses the read-only native `admin-ajax.php?action=gq_support_session` operation to check the session on open, focus, visibility changes, and explicit submission. Focus and visibility changes start at most one check per 5 seconds. An opaque binding ties the tab to the original account, login session and site. Only a matching cookie session with its current grant receives a fresh REST nonce. A changed session clears tab-memory draft text; lost grants or a failed check pause the form and preserve the draft with a copy affordance. No background polling, persistent browser draft storage, automatic write replay, or extra support REST route is introduced. The report form sends one in-memory Submission ID per intent and reconciles ambiguous responses with the same frozen body. It stops automatic reconciliation while closed, after three attempts, or after a refused session check or any rejected check (an unreachable session check is charged as an attempt); explicit retries after a failed delivery, or after a body conflict with no earlier ambiguous attempt, use a new key. Leaving the page unmounts the widget, so its private state never survives into a back/forward cache restoration. Full request-list and detail presentation belong to the projection workflow (#26).

Uninstall clears the current site's plugin-owned Reporter metadata as well as its tracked grants and options. The existing bounded multisite uninstall policy remains: a network-wide purge is a separate operator operation, rather than a synchronous loop over every site.
