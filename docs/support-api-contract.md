# Support API contract

Decision record for [issue #6](https://github.com/Quick-Release/gq-support/issues/6). It specifies the browser → WordPress REST contract and the WordPress → Worker transport adapter. [ADR 0009](adr/0009-project-repository-intake-and-reporter-scoped-projection.md) limits the surface to issue intake and a Reporter-scoped projection, and the [support security design](support-security-design.md) owns the authentication and authorization rules this contract relies on. [CONTEXT.md](../CONTEXT.md) defines the terms. This is a contract, not a claim that it is implemented.

## Routes

Namespace: `gq-support/v1`. The namespace is the version, and responses carry no separate version field. Routes are registered on `rest_api_init`, always, including on an unconfigured installation.

| Method and path | Capability | Purpose |
|---|---|---|
| `POST /requests` | `gq_support_submit_requests` | Create one Support request (idempotent per Submission ID) |
| `GET /requests?scope=mine` | `gq_support_submit_requests` | List own requests (default scope) |
| `GET /requests?scope=site` | `gq_support_view_site_requests` | List every request from this installation, read-only |
| `GET /requests/{id}` | own: submit; other's: view-site | Read one request |

Every other path returns 404. There are no receipt, message, state, reply, close/reopen, or attachment routes. Delivery outcome is a field on the request resource. Adding any of these routes needs a new decision (ADR 0009).

Every route has a `permission_callback` that checks the cookie session, the `wp_rest` nonce, current site membership, and the capability. Object access is checked again at the Worker for the installation plus either the attested Reporter subject or a freshly attested view-site grant. An unknown request, and a request outside the caller's scope, both return **404**, so the response never reveals that the request exists. `scope=site` never means cross-installation.

## Request and resource shapes

### Create

```http
POST /wp-json/gq-support/v1/requests
X-WP-Nonce: <wp_rest nonce>
Content-Type: application/json

{
  "submission_id": "3f0c2a4e-6b1d-4c1e-9a55-0d8e3f2b7c11",
  "summary": "Checkout button does nothing",
  "description": "On the cart page, clicking Checkout does nothing. I expected the payment step."
}
```

| Field | Rule |
|---|---|
| `submission_id` | Required UUIDv4, generated by the browser per draft and reused for every retry of that draft. |
| `summary` | Optional. One line, 1–120 characters after trimming. |
| `description` | Required. 1–10,000 characters after trimming. |
| anything else | Rejected (`additionalProperties: false`). There is no category, context, or attachment field in v1. Environment context is added server-side (#14). |

The whole request body is capped at 32 KB. Limits live in one constants file per side, and a shared fixture asserts they agree.

The Submission ID is a reference, not authority. The Worker scopes it to (installation, Reporter subject), so the same UUID from another Reporter is a different key.

### Resource

```json
{
  "id": "req_01J8Z6Q4M1ZC7",
  "submission_id": "3f0c2a4e-6b1d-4c1e-9a55-0d8e3f2b7c11",
  "title": "Checkout button does nothing",
  "summary": "Checkout button does nothing",
  "description": "On the cart page, clicking Checkout does nothing. I expected the payment step.",
  "created_at": "2026-09-28T10:00:00Z",
  "delivery": "delivered",
  "status": "open"
}
```

- `id` is an opaque service-issued identifier. It is never a GitHub issue number, URL, or repository name.
- `title` is `summary`, or the description's first line cut at a word boundary to about 80 characters.
- `delivery` is one of `accepted-pending`, `delivered`, `failed`, or `outcome-unknown`. `locally-unsent` is a browser-only state and never goes over the wire.
- `status` is `open` or `closed` once `delivered`, and `null` before that. GitHub is authoritative (ADR 0003).
- Timestamps are UTC ISO 8601. The browser formats them in the site timezone.
- Text is plain and is escaped when rendered. There are no comments, labels, assignees, or repository fields.

### List

`GET /requests?scope=mine&per_page=20&cursor=<opaque>` returns `{ "items": [Resource…], "next_cursor": "<opaque>|null" }`, newest first. `per_page` defaults to 20 with a maximum of 50. There are no totals and no `X-WP-Total`. A cursor is opaque and valid only for the same scope and caller.

## Create semantics

| Outcome | Response | Reporter sees (see domain design) |
|---|---|---|
| GitHub issue created synchronously | `201` + `Location`, `delivery: delivered` | "Open" |
| Intent durably recorded, not yet delivered | `202`, `delivery: accepted-pending` | "Received" |
| Repeat of a known Submission ID with the same body | The existing resource with its current code (`201`/`202`), and no second issue | per `delivery` |
| Same Submission ID, different body | `409 gq_support_idempotency_conflict` | "Not sent", and the draft gets a new key |
| Worker could not durably record | `503 gq_support_not_accepted` (retryable) | "Not sent" + Try again with the **same** key |
| Timeout or unparseable/ambiguous Worker response | `504 gq_support_outcome_unknown`, echoing `submission_id` | "Checking…" |
| An accepted intent later fails terminally | the resource with `delivery: failed` | "Not sent" + Try again with a **new** key |

Rules:

- Success is never inferred from `blocking => false`, from a transport return without a parseable body, or from a 2xx without a valid resource.
- **Re-POSTing with the same Submission ID is the reconciliation path.** The Worker either finds the existing intent or creates it exactly once. "Checking…" retries the same key automatically, at most 3 times with backoff and only while the panel is open, and then offers a "Check again" button. It never sends the report as a new issue (ADR 0003, ADR 0006).
- `201` versus `202` is left open for #11 to decide between synchronous and durable delivery. The browser handles both.

## Error catalogue

Every error is a `WP_Error` whose `data` is `{ status, correlation_id, retryable }`. Errors never include the upstream body, the Worker URL, exception text, credentials, or report content.

| HTTP | Code | When | Reporter sees |
|---|---|---|---|
| 401 | core `rest_not_logged_in` / `rest_cookie_invalid_nonce` | Session or nonce expired | "Your session expired. Reload the page to continue." Draft kept |
| 403 | `gq_support_forbidden` | Missing capability or site membership | Same as 401 |
| 400 | core `rest_invalid_param` / `gq_support_invalid_request` | Schema or limit failure | Inline field error |
| 413 | `gq_support_payload_too_large` | Body over 32 KB | Inline error |
| 404 | `gq_support_not_found` | Unknown or out-of-scope request | "Not found" |
| 409 | `gq_support_idempotency_conflict` | Same key, different body | "Not sent", new key on retry |
| 426 | `gq_support_plugin_outdated` | Worker no longer supports this plugin version | "Support needs a plugin update" |
| 429 | `gq_support_rate_limited` + `Retry-After` | Per-subject or per-installation limit | "Too many requests, try again later" |
| 503 | `gq_support_not_configured` | No connection, or the Worker rejected the installation credential | "Support is unavailable"; operator sees detail on the setup page |
| 503 | `gq_support_not_accepted` | Create: the Worker could not durably record | "Not sent" + Try again (same key) |
| 503 | `gq_support_unavailable` | Read: Worker down, timed out, or ambiguous | "Couldn't load. Refresh to try again." |
| 504 | `gq_support_outcome_unknown` | Create: timeout or ambiguous response | "Checking…" |
| 500 | `gq_support_internal` | Anything else | Generic error with correlation ID |

- A Worker authentication or signature failure is **never** returned to the browser as 401/403. That would look like an expired session and send the Reporter into a reload loop. It maps to `503 gq_support_not_configured`.
- Automatic retries follow `Retry-After`. A 429 is never retried automatically, and a write is never replayed after reauthentication (security design, test group 6).
- The status matrix covers auth expiry (401/403), rate limits (429), GitHub unavailability (`202 accepted-pending` if the intent is durable, otherwise `503 gq_support_not_accepted`), and ambiguous write completion (`504` plus same-key reconciliation).

## Caching

Every `gq-support/v1` response sends `Cache-Control: private, no-store` explicitly, rather than relying on core's logged-in no-cache default. WordPress keeps no transient or object cache of projections in the MVP, so every list and read goes to the Worker. Reads only happen when My requests is shown or refreshed.

## WordPress → Worker transport

`GQ_Support_Service_Client` is the one adapter. It uses WordPress's HTTP API and has no third-party HTTP client.

| Concern | Policy |
|---|---|
| Destination | Base URL is a plugin constant, overridable only by `GQ_SUPPORT_SERVICE_URL` in `wp-config.php` (staging, dev). It is not an admin-editable option, so a site admin cannot redirect signed traffic. HTTPS only. |
| Function | `wp_safe_remote_request()` (`reject_unsafe_urls`) |
| Redirects | `redirection => 0`. A 3xx is treated as an ambiguous response. |
| TLS | `sslverify => true` |
| Timeouts | 8 s for create, 5 s for reads. The browser's `apiFetch` timeout is about 15 s. |
| Response size | `limit_response_size` 64 KB. An oversized or unparseable response is ambiguous. |
| Worker path | `/v1/...`. The path version changes only on a breaking change, and `/v2` then runs alongside `/v1` until the fleet has migrated. |
| Version header | `GQ-Support-Plugin-Version`. Within v1 the Worker makes only additive changes and accepts every supported plugin version. Older plugins get 426. |
| Signing headers | `GQ-Support-Key-Id`, `GQ-Support-Timestamp`, `GQ-Support-Request-Id`, `Content-Digest` (RFC 9530, sha-256), `GQ-Support-Signature`. The signer is an injected dependency. Its canonical string, algorithm, clock window and replay store belong to #32. |
| Forwarded identity | The attested Reporter subject and, for `scope=site`, a freshly attested view-site grant. There is no WordPress nonce, cookie, email, username, or numeric user ID, and no browser-supplied installation, Client, or repository. |
| When calls happen | Only inside a `gq-support/v1` route callback. Never during page rendering, activation, or cron. |

WordPress → Worker payloads carry the same field names and limits as the browser contract, plus the attested identity and the server-side context from #14.

## Contract tests

Shared JSON fixtures in `contract/fixtures/` are the drift guard. There is no generated shared schema, because the two hops are different shapes and WordPress REST supports only a subset of JSON Schema. PHPUnit and the Worker test suite both run every fixture.

- Valid and invalid create payloads, covering each limit boundary, unknown fields, a missing or malformed `submission_id`, and multi-line summaries.
- Resource and list responses for each `delivery`/`status` combination.
- Version mismatch (old plugin → 426) and every error code in the catalogue.

The adapter is tested with `pre_http_request` stubs for 2xx, each Worker error, timeout, 3xx, oversized body, malformed JSON, and TLS failure. Each case checks the mapped browser error and that no secret or report content reaches the logs.

## Acceptance for implementation

- Each route in the table exists with a `permission_callback` and argument schema, and every other `gq-support/v1` path returns 404.
- Out-of-scope and unknown IDs return the same 404.
- Create is idempotent per (installation, subject, Submission ID). A conflicting body returns 409. A timeout returns 504, and a same-key retry never produces a second issue.
- The error catalogue, `Cache-Control: private, no-store`, and the transport policy are verified by tests.
- No external calls during unrelated page rendering or plugin activation.
