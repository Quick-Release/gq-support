# CI, compatibility and security verification

Decision for [research #19](https://github.com/Quick-Release/gq-support/issues/19), researched 2026-10-18 against checkout `bd1cd590edaaff93785dfd736a0ace3bcddd0324`. Prerequisites #3, #4, #6, #11, #12, #16 and #18 are closed. This records the release policy and missing implementation; it does not certify that every gate below already runs.

## Decisions

Extend the existing Composer, pnpm, DDEV, Playwright, Vitest and Miniflare harnesses. Real WordPress integration is mandatory: stubs alone cannot prove nonce processing, option autoload, capabilities or lifecycle behavior. Keep deterministic tests credential-free and required for pull requests; run real GitHub/Cloudflare smoke tests separately on reviewed main commits in the staging environment.

Keep WordPress 6.5 and PHP 8.0 as the declared minimums. Test WordPress-owned React at runtime rather than treating npm package versions as the supported WordPress runtime. Test actual distributable archives as well as the assembled tree. Use one always-running aggregate required check so path filters cannot leave required checks pending or accidentally bypass cross-language contract validation.

Current MVP remains plain-text submission, honest Delivery outcome and read-only open/closed Support status. GitHub comments, edits and internal metadata stay internal. Reporter replies and close/reopen mutations, Queues, R2, attachments and screenshots are deferred. Old issue wording about queue replay and replies means durable D1 recovery replay and negative assertions that these interfaces are absent, respectively. Adding those features requires their own decisions and tests.

## Supported-version and execution matrix

This is the selected project policy. A minimum compatibility promise does not endorse running an upstream end-of-life PHP version in production: PHP publishes its own [support lifecycle](https://www.php.net/supported-versions.php). Keep the floor until an explicit coordinated header/Composer/PHPCS/PHPStan change raises it.

The official [WordPress version API](https://api.wordpress.org/core/version-check/1.7/) returned **7.1.3** as stable and **6.5.13** for the 6.5 line on 2026-10-18. Resolve and record exact stable and previous-minor patch versions in a reviewed matrix file; scheduled refreshes propose changes. Do not silently redefine a release result with a moving `latest`. WP 6.5.0 remains a compatibility sentinel on isolated test infrastructure, not a recommendation for an unpatched production site.

| Lane | WordPress | PHP | Database / topology | Browser / frequency |
|---|---|---|---|---|
| Minimum API/runtime | 6.5.0 | 8.0 | DDEV default recorded DB; single site then subdirectory multisite | Chromium; required PR |
| Patched minimum line | 6.5.13 | 8.2 | Same; single site | Chromium; required PR |
| Current supported endpoint | 7.1.3 | 8.4 | Same; single site then subdirectory multisite | Chromium; required PR |
| Intermediate PHP coverage | 7.1.3 | 8.1, 8.2, 8.3 | Single site; integration/contract only | Required PR; no redundant full browser matrix |
| Previous WP minor | 7.0.7 | 8.4 | Single site | Chromium smoke; nightly and pre-release |
| Database/cache variants | 7.1.3 | 8.4 | MySQL 8.0 and pinned MariaDB baseline; persistent object cache on/off; multisite subdomain variant | Nightly and pre-release; isolate DNS fixture |
| Alternate browsers | 7.1.3 | 8.4 | Single site | Locked Playwright Firefox and WebKit; nightly and pre-release |
| Forward compatibility | WP beta/nightly; stable on PHP 8.5 | Matching compatible PHP; single site | Disposable only | Nonblocking canary until explicitly promoted |

For mandatory lanes PHP 8.0–8.4 is supported; higher PHP versions are unclaimed canaries until the runtime/static range is extended. All stable WordPress releases from 6.5 through 7.1 are in the intended compatibility range; endpoints plus the previous-minor lane are the economical regression strategy, not proof of every Cartesian combination. On a newly supported WordPress minor, require the full pre-release suite before updating `Tested up to`. Record skipped incompatible upstream combinations explicitly rather than letting their failures silently disappear. The API declares PHP 7.4 as the minimum for WP 7.1.3, so these current PHP combinations meet that WordPress prerequisite.

Use Node 26, pnpm 12, Composer 2 and DDEV 1.25.4 as the current repository toolchain, pin package/browser engines by lockfile and record patch versions. DDEV should receive a per-job PHP override before `start`; fresh per-job storage is essential because `run.sh` deliberately reuses an existing downloaded WordPress tree. Every matrix cell must prove its actual PHP/WP/database versions in its report.

WordPress 6.5's registered React runtime is 18.2.0 in [core script-loader source](https://github.com/WordPress/wordpress-develop/blob/6.5/src/wp-includes/script-loader.php). The compatibility interface is `wp.element` (`createRoot` and the hooks used by the app), `wp.apiFetch`, `wp.i18n` and `wp.a11y`, not the current npm versions of those packages. Preserve [ADR 0011](../adr/0011-wordpress-native-react-runtime.md): classic JSX, no `react-jsx-runtime` dependency and no bundled second React. Verify the complete extracted dependency graph resolves on 6.5.0; assert request order, shared runtime identity on WooCommerce/block-editor screens and no React 19-only API. [Dependency extraction](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dependency-extraction-webpack-plugin/) generates runtime dependency/version manifests; those manifests are an executable compatibility boundary.

Multisite is supported **per site** with independent installation identity, signing key, options, Reporter subjects and capabilities. Network activation may not enroll every site or cause unbounded loops; network admin has no Reporter launcher. Required tests cover two subsites sharing numeric user IDs, same Client/repository but distinct Slots, newly created site, `switch_to_blog()`/restore, site removal versus user deletion, and bounded per-site uninstall. Existing `multisite.sh` is the starting harness. No claim of a network-wide reporting UI or network-wide remote purge is introduced.

Browser support follows current maintained desktop Chromium/Chrome/Edge, Firefox and Safari engines. Automated Firefox/WebKit builds are useful coverage, not certification of every installed browser version; manually smoke current Safari and Edge before first production release and after loader changes. Do not promise Internet Explorer. Playwright pins compatible [browser revisions](https://playwright.dev/docs/browsers); install them from the locked version rather than arbitrary system browsers.

## Deterministic fixtures and failure injection

Reuse [contract/fixtures](../../contract/fixtures) and [fake GitHub](../../worker/test/fake-github.ts); avoid independent copies of schemas in PHP and TypeScript. Include two Reporters A1/A2 in Slot A, Slot B in the same Client and same repository, and Slot C in a different Client/repository. Use overlapping WordPress user numbers but unrelated opaque subjects. Include one Support manager with explicit site visibility and an administrator denied reporting or settings capability. The same email on A and C must not become a service identity.

Use seeded non-secret keypairs, fixed clocks, explicit random/UUID sources and controlled backoff. Supply boundary cases at timestamp skew, byte versus Unicode-code-point limits, maximum pagination, expired cursor, malformed JSON, incompatible response version and content type. Scope cursors to Slot/Reporter/view; modified or reused cursors must not cross boundaries. Each test gets a fresh migrated local D1 and restores WordPress state in teardown. Add barriers/failpoints for races rather than sleeps; advance fake time to expiry. Preserve real SQLite constraints and transaction behavior rather than replacing D1 with an array.

Run fake GitHub as a local adapter with scripted status/body/headers, response loss after a recorded side effect, pagination, slow/hung socket, duplicate markers and an audit of method/path/body. Keep ordinary PR networking limited to dependency setup and local fixtures: accidental GitHub create attempts fail the test. For Worker integration test the production `fetch` and scheduled entrypoints in workerd/Miniflare as well as calling services directly. Existing Node-Vitest plus Miniflare D1 remains supported; switching wholesale to another Vitest pool is unnecessary. Cloudflare distinguishes [unit, integration and runtime testing](https://developers.cloudflare.com/workers/testing/); local tests do not prove deployed account configuration.

Real WordPress dispatch must test registration on `rest_api_init`, allowed methods/argument validation, `permission_callback`, real role/meta-cap resolution, settings/nonces, `pre_http_request` adapter options and WordPress error conversion. HTTP tests remain necessary because merely assigning the current test user cannot prove cookie authentication. Missing `wp_rest` nonce makes cookie-authenticated REST requests unauthenticated; nonce checks do not grant capabilities ([WordPress REST authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/)). Filters/hooks are trusted-extension seams, but mutated payloads/responses are revalidated; a filter must not override ownership, destination or response allowlist.

## Adversarial and recovery release checklist

#33 owns deterministic adversarial coverage. Add tests next to each feature; this checklist is the common release contract, not a new monolithic framework.

1. **Authentication and scope:** forged Client/Slot/repository/Reporter headers and body fields; A1 reads A2; A reads B in same repository; A reads C; enumeration through errors, receipt IDs, caches and cursors; missing/expired nonce, logout, membership removal and revoked signing key. Reject canonical-string/path/query/body changes and wrong digest before resource access. Distinguish intended idempotent same-key re-POST from replaying a captured signed transport request. Expired transport signatures never become a second acceptance.
2. **Fail closed:** quota/replay/key-store/D1 outage never bypasses authorization or claims acceptance. Wrong deployment stage/account mapping, unknown key, public/archived/inaccessible repository and installation removal suspend or reject safely. Ed25519 rotation validates key-ID agreement and constants-backed as well as generated WordPress keys. Cloned-origin detection removes the copied credential; it cannot act as production.
3. **Input and output:** test HTML, script tags, event handlers, malformed Markdown, `javascript:`/`data:` links, raw internal URLs, Unicode/control characters, huge bodies and malformed upstream JSON. Plain-text submitted content stays inert in browser and safely delimited in GitHub issue bodies; embedded correlation-marker text cannot impersonate a service marker. No attachment/upload/comment/status-write endpoints exist; random identifiers or upload fields cannot enable them.
4. **Secret/log leakage:** synthetic unique canaries for App PEM, installation private key, provider token, cookie/nonce, Submitted text, Reporter subject/hash and Submission ID. Capture logs, responses, bootstrap HTML, compiled assets, exception paths and artifacts. Permit only the privacy design's operational identifiers/error class/status. Never solve a test by logging raw upstream requests.
5. **Durable delivery crash matrix:** fail before acceptance commit (no receipt), after commit/before background dispatch (minute sweep finds work), after claim/before GitHub POST, after GitHub side effect/before response, after response/before mapping write, and after mapping write/before completion acknowledgement. Concurrent sweep/prompt execution and expired leases must not issue competing creates. Existing D1 uniqueness alone is insufficient for a remote side effect.
6. **Retries and uncertainty:** same key/same payload yields one logical request, changed payload conflicts; known non-creation failures may retry within the design's bounded policy and Retry-After, while timeouts/5xx/connection loss after potential send enter uncertainty. Reconcile first-line intent markers through creator-filtered paginated issue listing, not Search. Positive match associates; duplicate matches or negative scans require review; no empty scan proves non-creation. Uncertainty survives 24 hours and operator intervention never silently creates a second issue. Manual replay checks revocation, suppression, mapping safety, original intent and attempt history again.
7. **Status/webhook security:** verify `X-Hub-Signature-256` over exact raw bytes before JSON parsing or D1 access; reject missing, wrong algorithm, malformed hex, wrong length, altered bytes and stale previous secret. Accept current/previous secret only in the explicit rotation window. [GitHub signature validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) documents the raw-payload HMAC boundary. Signed events are still routed by trusted numeric IDs and allowlisted actions. `issue_comment`, issue edits/opened hints, labels and assignees do not project content. Webhooks mark refresh, never copy payload status; sweeps/read-only GitHub fetches establish status. Reordered/duplicate deliveries cannot roll back newer `updated_at`. Signed safety events suspend immediately; malformed signatures cause no D1 access. Acknowledge refresh writes only after persistence; failure gives 503. No per-delivery inbox or automatic delivery-log API is required.
8. **Sweep completeness:** paginate/resume interruption, overlap windows, rate limits, missed webhook, daily scan of still-open requests, transfer/delete outside the mapped repository, suspended mapping, revoked installation and stale projection. Missing rows never get reconstructed from provider payloads. Operator alone lifts suspension. #12 freshness targets remain ≤17 minutes by sweep, p95 ≤2 minutes with webhook hint, and ≤24 hours for unannounced transfers/deletes; measure those in staging rather than asserting fake-clock tests prove wall-clock delivery.
9. **Erasure/restore:** all pending/failed/in-flight/outcome-unknown/delivered/tracking-lost states, concurrent delivery, delayed issue discovery, failed redaction, retitled issue, comments and edit-history residual copies. Suppress new creates immediately and purge text after draining active execution; unresolved remote outcome remains incomplete. Restore a pre-revocation/pre-erasure snapshot, apply the separate suppression ledger before traffic or background work, and confirm no erased record or create resurrects. Delayed webhook, sweep, replay and fresh enrollment cannot defeat the tombstone. Resolved tombstone TTL begins after resolution; unresolved cleanup survives 45 days. #46 owns this implementation.
10. **Retention/offboarding:** closed over 12 months purges; reopen resets close retention; never-confirmed-delivered text expires 12 months after acceptance, with only restricted reconciliation metadata retained. Grace-period offboarding purges the Slot after 30 days and suppresses delivery without deleting Client-owned GitHub issues. Export/erase on the same email in another site affects no other Slot. User removal from one multisite site differs from deleting the user; callbacks keep `items_retained` honest while remote work or residual copies remain.

## Installed package and lifecycle smoke plan

Extend the existing allowlist assembler and tested-artifact handoff. Composer branch/tag distribution remains supported. Produce an installable `gq-support.zip` for verification from the same candidate tree even if Composer remains the publishing channel. Reject unexpected PHP/runtime files, `.env`, credential/private-key files, `.git`, tests, app sources, `node_modules`, development `vendor`, logs and sourcemaps containing source/secrets. `composer.json` is intentional runtime distribution metadata. Use an explicit expected manifest and denylist, with a negative-control missing manifest/key leak/archive traversal.
2. Assert version/header/constant/Stable tag agree with requested release; `Requires at least`, PHP minimum, text domain, required `gq-design` dependency and license metadata agree. Include launcher JS/CSS, compiled app JS/CSS/RTL, `index.asset.php`, required PHP classes/uninstall and packaged translation JSON/MO. Check every dependency handle resolves on minimum WordPress; verify no `react-jsx-runtime`, duplicate React, or developer-only runtime import. Compare archive digest after transport/extraction.
3. Fresh disposable WordPress installs ZIP by `wp plugin install /path/to/gq-support.zip`; keep test-only probes and dependency fixture outside the installed directory. Without gq-design, activation must fail without creating connection state. With the fixture activate normally; visit public, admin, REST and WP-CLI contexts. Missing unsupported PHP/WP versions must refuse cleanly, not fatal or mutate state.
4. Install the previous approved release archive, seed documented legacy/current state, custom-role capabilities, Reporter subjects and harmless unrelated sentinel options/events. 5. Deactivate/reactivate: retain site identity and connected state, stop plugin-owned work, no remote destructive operations. Delete/uninstall: remove only locally owned options/keys/grants under the documented bounded-site policy; preserve unrelated roles/options/events, other sites, GitHub issues and shared infrastructure. 6. Run browser loader/submission smoke, Plugin Check and size/counter gates on the archive-installed copy at minimum and current endpoints. Runner must prove the active file path comes from the extracted archive, not a source symlink. Preserve the archive, SHA-256 and sanitized result manifest.
