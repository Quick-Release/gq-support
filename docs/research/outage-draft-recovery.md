# Outage behavior and draft recovery

Decision for [Define outage behavior, draft recovery, and whether a local WordPress outbox is needed](https://github.com/Quick-Release/gq-support/issues/17), part of [WordPress-native, GitHub-backed client support](https://github.com/Quick-Release/gq-support/issues/1). Reviewed 2026-10-18 against the current repository and the primary sources linked below. This records planning decisions and implementation acceptance criteria; it does not claim these behaviors are all implemented or authorize production data collection.

## Decision and delivery promise

Keep the MVP draft in the current support interface's memory, scoped to the original WordPress installation, Reporter account and login session. Preserve it across panel close/reopen and support transport failures while that document and session remain current. Defer browser persistence, a durable WordPress outbox, Action Scheduler and support-delivery WP-Cron jobs. D1 remains the single durable delivery outbox selected in the [delivery design](../support-delivery-design.md).

The Reporter-facing promise is:

> Your draft stays in this support panel while this page and your session remain open. Copy it before leaving or reloading. “Received” means the service saved your report and will attempt delivery; it does not mean the team has received a GitHub issue yet. “Open” or “Closed” means issue creation was confirmed. An uncertain result needs checking and may need staff review.

Before D1 acceptance there is no eventual-delivery promise. Closing a tab, navigating, refreshing, a browser crash or a lost session can lose an unsent draft and its Submission ID. After atomic D1 acceptance, delivery no longer depends on the browser or WordPress remaining available, but provider failure, safety controls and uncertain creates can prevent completion. Normal delivery in seconds and minute recovery are operational targets, not guarantees. Never describe a Queue, background wake-up, browser cache or nonblocking HTTP return as offline draft protection. These boundaries follow [ADR 0003](../adr/0003-durable-acceptance-separates-delivery-from-status.md) and [ADR 0019](../adr/0019-uncertain-creates-require-review.md).

## Failure matrix

“Memory” below means only the existing document's identity-scoped state. “Frozen intent” includes Summary, Description, Submission ID and optional `supersedes_id`, exactly as sent. All recovery respects current authorization. A failed check never silently adopts a different account or session.

| Boundary / failure | Visible state | Retained data | Retry / recovery | Operator action |
|---|---|---|---|---|
| Offline or WordPress unreachable before explicit Send; session precheck fails | Session needs checking; draft available to copy; no acceptance claim | Memory draft; no durable copy | User explicitly checks/retries when reachable; no reconnect-triggered write | None unless outage persists |
| Browser disconnect or timeout after Send might have reached WordPress | Checking; eventual Check again | Frozen intent in memory; D1 may already contain it | At most three automatic same-key re-POST checks while open and authorized; then manual check | Investigate recurring connection failures without requesting report text in logs |
| WordPress DNS/TLS error, blocked outbound HTTP, invalid/slow endpoint, Worker outage | Checking for an attempted create unless non-acceptance is proven; reads show Couldn't load | Frozen intent; possible D1 record | One bounded transport call; same-key checks, never a fresh logical intent | Repair endpoint/network/allowlist/TLS; never disable certificate validation |
| Explicit durable-intake failure, `503 gq_support_not_accepted`, with no earlier ambiguous attempt | Not sent; Try again | Memory draft and same key | Manual retry with same frozen key/body; no automatic network loop | Investigate D1/provider acceptance health |
| A later check says not accepted after an earlier ambiguous attempt | Checking / unresolved | Frozen intent, possibly existing D1 record | Later rejection does not prove the earlier attempt failed; preserve identity and ambiguity | Inspect intake record if bounded checks cannot resolve |
| D1 commits, response or post-commit wake-up is lost | Checking until valid replay; then Received | D1 request and intent; memory until acknowledgment | Same-key replay discovers commit; service minute sweep recovers without browser | Observe sweep age/errors; no manual duplicate create |
| Valid `202 accepted-pending` | Received; delivery pending; Support status absent | D1 owns Submitted text; clear composer on valid acknowledgment | Manual resource/list refresh only; no acceptance re-POST or pending polling loop | Known-undelivered pending reaches 24 hours: fail and alert per delivery policy |
| GitHub down, rate limited or temporarily rejecting with proof of non-creation | Received; pending | D1 request/intent | Service owns bounded known-non-creation retries and rate delays, up to 24 hours from acceptance | Investigate excessive oldest-due age and provider limits |
| GitHub create times out, malformed success, ambiguous 5xx or abandoned dispatch | Delivery outcome unknown; staff review; never Open | D1 request and restricted attempt/reconciliation state | Read-only service reconciliation; no new GitHub POST. Valid resource is already acknowledged intake; manual GET refresh | Alert at 15 minutes, immediate for multiple/conflicting matches; handoff at 24 hours unresolved |
| GitHub terminal validation/permission failure | Not sent / failed resource; no Support status | D1 retains failed request under privacy policy; failed text can be explicitly reused | Explicit replacement gets new Submission ID plus `supersedes_id`; no automatic new report | Correct mapping/App permission/configuration, suspend unsafe mapping; audited recovery only |
| WordPress installation credential expired/revoked, copied-site identity or enrollment problem | Support unavailable; setup action for authorized administrator | Memory draft; already accepted D1 requests survive credential rotation | Stop checks on configuration error; no login/reload loop or silent re-enrollment | Reconnect/re-enroll approved installation; accepted work remains independent |
| Session/nonce check unavailable, grants lost, REST 401/403 | Paused; copy draft before reload; no automatic write replay | Memory draft retained while same identity cannot yet be disproved | Session read can validate only original binding; explicit user action after successful recheck, no automatic resume of write | Restore legitimate grant if appropriate; never bypass permissions |
| Different account/login session/site detected; logout; page departure | Clear old text and intent; show session-change explanation | No old draft exposed in restored UI; remote accepted record remains scoped | Never transplant an old key/body into new identity; new session may list its own resources explicitly | If outcome was uncertain, investigate before requesting duplicate manual submission |
| Tab close, reload, navigation or browser termination | Warn before ordinary departure where feasible; no promise of recovery | No guaranteed local draft; already committed D1 request survives | On return explicitly load My requests before composing a possible duplicate; manual help if lost receipt cannot be identified | Use trusted service records for uncertain report; never infer failure from missing browser state |
| Back/forward cache restoration or tab frozen then resumed | Revalidate binding before reveal/send; stale text cleared on departure | No reliance on memory survival as persistence | No automatic write on `pageshow`, focus or visibility; a read-only session check may resume UI | None normally |
| App script/CSS blocked, fails to load, or never completes | Bounded launcher failure with Retry and independent help link; ordinary admin remains usable | Existing page unaffected; no report accepted by loader | One explicit loader attempt at a time; retry only on user action | Repair packaged assets/CSP/cache/release; use fail-safe if needed |
| Request list/read fails | Couldn't load; Refresh; never empty-list success | Already rendered projection only while identity remains current; D1 unchanged | Manual GET refresh; no read retries/polling while hidden | Investigate prolonged outage; last observed Open/Closed is not a fresh provider check |
| 400/413 local or remote validation failure | Inline field error; no sent claim | Editable memory draft after definite validation rejection | Correct and explicitly send; retain frozen payload if a previous attempt remains unresolved | None unless schema drift |
| 429 / Retry-After | Too many requests; show retry guidance | Same draft/key; preserve any earlier ambiguity | No automatic retry; explicit action only after stated delay | Investigate abuse/limits; do not reset quota through re-enrollment |
| 409 body conflict | Explain mismatch; stop automatic checks | Preserve original frozen intent if any earlier result is ambiguous | Conflict alone never proves old intent failed. Resolve original intent before offering a fresh-ID send; never mutate same-key body | Investigate accidental body mutation or key reuse; assist unresolved recovery |
| WordPress broken or inaccessible; plugin disabled | Independent contract contact remains available outside WordPress | Reporter may retain their own copy; D1 accepted work unaffected | Reporter contacts staff manually; no automatic email fallback or hidden report forwarding | Restore WordPress or disable support; reconcile uncertain reports before a manual replacement |

“Checking” is transport uncertainty about intake; `delivery: outcome-unknown` is confirmed intake with uncertainty about the GitHub side effect. They are separate UI states even though both require caution. A negative marker scan never proves GitHub non-creation. A 24-hour deadline ends automation, not uncertainty.

## Bounded requests and retry ownership

Retain the [API contract](../support-api-contract.md) values: one `wp_safe_remote_request()` per WordPress route operation; create timeout 8 seconds, reads 5 seconds; browser POST deadline 15 seconds. A Send operation can spend up to roughly 25 seconds across the separate 10-second session precheck and 15-second POST deadline; 15 seconds is not an end-to-end click deadline. HTTPS, certificate verification, no redirects, 64 KB response cap and no upstream exception/body leakage remain mandatory. WordPress's documented HTTP interface exposes these controls and returns `WP_Error` for failures; `blocking: false` omits the response and therefore cannot establish durable acceptance ([HTTP API source/reference](https://developer.wordpress.org/reference/classes/wp_http/request/)). Hosting filters and network/runtime suspension can affect elapsed wall time; these are configured request bounds, not an end-to-end availability SLA.

Session checks use a 10-second browser deadline. Concurrent checks share one promise. Opening the panel, focus/visibility return and explicit Send may check only the original session binding; coalesce focus/visibility events to at most one completed activity-driven check per 5 seconds, with no trailing timer while hidden. Explicit Send may require a fresh check and cannot be suppressed by that event cooldown. Never poll sessions. A session check is read-only and goes to WordPress, not a service health endpoint.

For ambiguous intake only, schedule at most three automatic same-key re-POST attempts after the previous attempt settles, at 1, 2 and 4 seconds respectively (or later if valid Retry-After requires it). At most one write is in flight. This is four maximum POSTs including the initial send, with up to four session checks; the bound is on attempts, not real elapsed time. Charge an automatic attempt when dispatched, including a failed precheck; do not reset its budget by closing/reopening, changing tabs, focus, visibility or network reconnection. Pause timers while closed or unauthorized; stopping a request client-side does not revoke remote acceptance. The manual Check again button makes one attempt and does not replenish the automatic budget. Never layer TanStack/apiFetch/global retry wrappers over these writes or let nonce refresh replay one.

`429`, authentication, configuration, version and definite validation errors stop automation. Honor valid Retry-After on manual retry as well; malformed values must not cause a hot loop. A failure of the reconciliation request does not resolve a preceding ambiguous send. A valid pending or outcome-unknown resource stops intake checks and hands recovery to the service. My requests and detail views use manual GET refresh. Keep unrelated pages, a closed panel and idle tabs free of support polling or health probes.

The service owns delivery after D1 acceptance: prompt best-effort wake-up plus minute D1 recovery sweep, known-non-creation retries up to 24 hours, and read-only unknown-outcome scans around 1/5/15/60 minutes then hourly through 24 hours. Keep that policy in the delivery design; the browser must not duplicate it. WordPress deactivation or key rotation cannot cancel accepted work; erasure, offboarding, explicit authorized cancellation and repository safety checks can suppress new dispatch.

## Draft lifetime, privacy and alternatives

| Alternative | Protects | Cannot promise / cost | Decision |
|---|---|---|---|
| Identity-scoped in-interface memory | Panel close/reopen, recoverable transport/session-check failure in the current document | No reload/tab-close/crash recovery; text lives in page memory | **MVP**; explicit warning and copy/manual-select affordance |
| Optional session/browser persistence | Could restore text and frozen intent after reload if storage survives | Browser policy/quota/deletion, same-origin script access, cross-session disclosure, migration and cleanup complexity; not delivery | **Deferred** until demonstrated lost-draft need and privacy review |
| Durable WordPress outbox | Could retain an acknowledged local report after navigation even while Worker is unavailable | Does not help browser→WordPress outage; adds content storage, scheduling, claims, privacy, restore and admin operations; not guaranteed prompt execution | **Deferred**; reopen only for an explicit post-navigation eventual-delivery requirement |

The HTML storage standard distinguishes session and local storage, permits storage writes to fail and does not provide a cross-window locking mechanism. Same-origin sharing is not a Reporter authorization boundary ([WHATWG Web storage](https://html.spec.whatwg.org/multipage/webstorage.html)). Therefore persistent storage is not a small switch or a substitute for durable intake. Any future option must preserve the frozen Submission ID and body, use installation + Reporter + session scoping verified before restoration, explicitly disclose local storage, and expire drafts after at most 24 hours (a proposed future bound, not existing retention). Cleanup must cover acceptance, discard, expiry, logout/session change, grant removal, erasure and offboarding. Never store cookies, nonces, credentials or signing material. Storage errors must fall back to memory without losing current text. Do not claim encryption protects data from same-origin scripts when its decryption secret is available there. Default remains off; no IndexedDB/service worker/background sync is approved.

For the MVP, clear text, intent, rendered private resources and automatic callbacks on a confirmed identity/session/site change and page departure; generation guards must ignore late responses. Pause and retain on a failed check or lost grant, showing a copy affordance without exposing another identity's text. Never write automatically after reauthentication. While unresolved, keep the exact original payload immutable; editing, removing `supersedes_id` or generating a fresh ID is not a retry. Explicit failed-resource replacement follows the API supersession rules.

Provide Copy draft on unsent, paused and unresolved states, with an accessible selectable plain-text fallback if Clipboard API fails. Explain that copying creates a Reporter-controlled copy outside automatic erasure. Do not put report content in contact URL query parameters, mailto bodies, analytics, browser logs or error reports. If uncertain text was lost, instruct the Reporter to check their own requests and contact staff about uncertainty before sending another report. Similar wording or an empty list alone cannot reliably prove non-creation.

A conditional unsaved-work `beforeunload` prompt may help ordinary navigation, but delivery and security must not depend on it. Browser lifecycle permits termination without reliable unload execution; Beacon only reports queueing for transfer, not server acceptance ([HTML lifecycle](https://html.spec.whatwg.org/multipage/document-lifecycle.html), [Beacon specification](https://w3c.github.io/beacon/#sendbeacon-method)). Do not send support reports during unload with Beacon or fetch keepalive. Browser online/offline state is a hint rather than proof of reachability ([HTML network state](https://html.spec.whatwg.org/multipage/system-state.html#navigator.online)); network events must never trigger a new write. Test back/forward cache separately because a surviving document can otherwise expose stale private memory.

## Why no WordPress scheduler or local outbox

Core WP-Cron normally checks due tasks on page loads, so an idle or inaccessible installation cannot promise prompt recovery ([WordPress Cron](https://developer.wordpress.org/plugins/cron/)). A system scheduler could improve triggering, but would introduce an installation operations requirement and still cannot deliver through an unavailable Worker. Action Scheduler is a separate library with its own installation, tables and runner; its default execution includes WP-Cron and admin-request loopbacks, rather than a new core API ([Action Scheduler usage](https://actionscheduler.org/usage/), [runner behavior](https://actionscheduler.org/)). Neither earns inclusion when D1 already owns durable accepted work and the MVP promises no local acceptance.

Never use Transients for an outbox: expiration is a maximum lifetime and values can disappear earlier, including through an external object cache ([Transients API](https://developer.wordpress.org/apis/transients/)). Do not alter core Heartbeat intervals or piggyback delivery onto Heartbeat. A short-lived privacy-export cursor or bounded lifecycle erasure retry is a different responsibility, not permission to introduce local report delivery jobs.

If a later requirement mandates durable local acceptance, revisit this decision before implementation: specify a new honest “Saved on this WordPress installation” state, bounded non-autoload storage and backpressure, transactional claims, same-key remote replay, short explicit retention, encrypted-content key custody and its limits, privacy exports/erasure, copied-site and backup/restore suppression, current-identity authorization and operator recovery. Determine maximum rows/bytes and eviction/rejection policy from load and privacy needs; never silently evict acknowledged unsent reports. Define retry owner and a real external runner if prompt idle-site recovery is promised. Deactivation must unschedule only plugin-owned hooks with exact arguments (`wp_clear_scheduled_hook`) or cancel only its Action Scheduler group, release claims safely and preserve retained records until explicitly purged; uninstall must remain bounded and documented. Core documents deactivation cleanup separately from uninstall ([hooks](https://developer.wordpress.org/plugins/plugin-basics/activation-deactivation-hooks/), [scheduled-hook cleanup](https://developer.wordpress.org/reference/functions/wp_clear_scheduled_hook/)). No such report jobs exist in the current MVP.

## Independent help and support fail-safe

Require an Operator-verified, existing Client contract contact before production onboarding: an approved external help address/URL or phone route reachable without WordPress, this plugin, its Worker or GitHub intake. Supply it to authorized Reporters in onboarding/contract material they can keep outside WordPress; verify it from a separate device during a WordPress outage drill. The repository does not establish a real address, so none is invented here. [Define per-client observability, safe rollout, updates, and recovery runbooks](https://github.com/Quick-Release/gq-support/issues/20) owns recording the per-Client route, who answers it and how it is tested. An unfilled contact field is a production-readiness failure, not permission to provision a new provider.

Store the verified contact in local Operator-managed `GQ_SUPPORT_HELP_URL` and `GQ_SUPPORT_HELP_LABEL` constants: URL at most 2,048 bytes with an explicitly allowed HTTPS, mailto or tel scheme, label at most 120 characters, no credentials or report/identity prefill. Validate on use and escape for output; never fetch it from the support provider during rendering. Show the same approved contact as a plain server-rendered link in the eligible support launcher fallback and setup page, usable when the app assets fail. An external link must not include report text, account identifiers, signed credentials or a prefilled report body. Staff receiving an uncertain-submission report checks trusted records before arranging a replacement; ordinary email is a human alternative, never an automatic submission transport. Public visitors receive no support assets or contact discovery from the widget.

Add a support-only local fail-safe, `GQ_SUPPORT_DISABLED` in `wp-config.php`, honored before launcher/app setup and before any support outbound transport, including explicit enrollment/status operations. It returns sanitized `503 gq_support_disabled` with `retryable: false` (an explicit catalogue extension) for authenticated support endpoints and leaves the local setup page explaining the disabled state and independent contact. Keep existing permission/session/no-store gates; it never makes an endpoint public or reveals another Reporter's content. It makes no remote health calls and has no effect on WordPress content, checkout, login, cron or core Heartbeat.

For a deployed plugin failure before that gate can run, the authorized site maintainer can deactivate only GETQUICK Support through normal WordPress administration or their existing WP-CLI/hosting access. Follow the site's incident runbook if WordPress cannot bootstrap. Disabling/deactivating does not erase local credentials, cancel previously accepted service work or offboard a Slot. Disconnect/uninstall/offboarding keep their distinct [privacy lifecycle](../support-privacy-design.md) meanings. Service-side repository suspension protects new dispatch and is not a substitute for a local fail-safe.

## Repository reconciliation and implementation ownership

The inspected browser already holds draft/intent memory, freezes payload during uncertainty, checks the original session, caps automatic intake checks at three and uses a 15-second POST deadline. The PHP adapter already sets 8/5-second timeouts, TLS verification, zero redirects and a response cap; lifecycle deactivation currently owns no schedules. These are useful foundations, not proof of the full failure matrix.

Implementation is assigned to [Harden support draft recovery and add a local fail-safe](https://github.com/Quick-Release/gq-support/issues/67), coordinated with the projection slice. The lifecycle verification ticket owns integration/release evidence rather than a second implementation. Remaining tensions to resolve:

Its automatic retry timer can be restarted by visibility; verify that the three-attempt budget survives all UI changes and manual checking never replenishes it. ### Implemented in #67

[Harden support draft recovery and add a local fail-safe](https://github.com/Quick-Release/gq-support/issues/67) resolved the browser and fail-safe tensions above:

- A valid `outcome-unknown` receipt is accepted intake: the panel shows **Delivery needs review** in My requests and makes no further create. A receipt is acknowledged only with the matching key, a valid delivery/status pair and `201` exactly when delivered. Every accepted receipt switches the panel to My requests, whose Refresh is the manual GET.
- A rejection after an ambiguous send, including 409, keeps the original key and frozen payload and ends automatic checks; only Check again re-sends it. Retry-After also holds back manual sends, with a message instead of a timer. A session check WordPress refuses ends the automatic budget; one that cannot reach WordPress is charged as an attempt and keeps the intent in Checking, without reload advice, and a send before dispatch says the site could not be reached.
- `pagehide` unmounts the app, open or closed, so the draft, intent, request list and timers are gone before a back/forward cache snapshot; the next open starts a fresh panel and session check. Focus and visibility start at most one session check per 5 seconds; opening the panel and Send always check.
- The composer discloses the draft's lifetime and offers Copy draft whenever it holds text, with a selected read-only text fallback when the Clipboard API is denied. No `beforeunload` prompt was added: it is optional above, and it could block ordinary navigation in automated browsers.
- The launcher gives each explicit attempt 10 seconds in total, keeps one load per asset across attempts so a late load is reused rather than inserted twice, and lets only the current attempt mount or report. Its error shows the server-rendered contact.
- `GQ_SUPPORT_DISABLED` is checked in the launcher, REST dispatch, enrollment, connection test, disconnect, erasure refresh and the service adapter itself, so privacy export and erasure calls fail like an unreachable service while it is set. A Reporter who would have the launcher sees a core admin notice with the contact instead. The setup page shows the disabled state and the contact, and hides its service actions. `GQ_SUPPORT_HELP_URL` must be an `https:` URL with a host and no credentials, or a `mailto:` address or `tel:` number, with no query string; a missing label falls back to the host, address or number.

## Implementation acceptance tests

Use controlled WordPress HTTP stubs, a fake service/GitHub and deterministic browser clocks/failure injection; no live Client text or credentials. Tests assert the user-visible consequence and outbound count, rather than mirroring hook internals.

1. With all providers unreachable, anonymous/public and unrelated admin pages render without support network requests or provider health checks. Closed panel, repeated focus, reload and network events cause no delivery traffic; approved launcher size/idle gates still pass.
2. Compose, close/reopen and switch UI views: identical text remains only in the same current document/session. Offline session precheck keeps copyable text and makes no POST. Reload/navigation/tab termination show the documented loss boundary; no persistent storage contains Submitted text or Submission IDs.
3. Send, commit remotely and drop the response. Verify at most three automatic checks at 1/2/4-second minima, one concurrent write, identical complete payload/key/predecessor each time and one D1 record/intent/quota debit/GitHub issue. Hide/reopen and manual Check again never reset automatic budget. A queued timer cannot dispatch after identity change or closure.
4. Distinguish malformed response/timeout (Checking and same-key path), `202 accepted-pending` (Received and stop intake checks), and valid `202 outcome-unknown` (accepted under review and no automatic re-POST). No Open/Closed before confirmed creation; no false empty-list success on read failure.
5. After ambiguity, inject `not_accepted`, 429, 401/403 and 409 on later checks: none proves old failure, mutates the frozen intent or silently creates a fresh key. Respect Retry-After and stop automation. After definite failed resource, explicit replacement carries a new key plus the same frozen `supersedes_id` throughout its own recovery.
6. Exercise blocked outbound HTTP, DNS/TLS error, timeout, redirect, malformed JSON, oversized body and worker commit ambiguity. Assert adapter bounds and sanitized catalogue mappings, response no-store, fresh signing request IDs for each same-submission replay and no report text/secrets in logs. Never turn off TLS to recover.
7. Lose nonce, cookie, membership or grant while sending/checking. Preserve memory on transient failure, stop automation and require explicit action after a successful original-session check. A confirmed changed account/session/site clears text, private resources and intent; delayed callbacks cannot restore them. Test pagehide and BFCache return while both open and closed, and logout in another tab.
8. Clipboard permission denial retains a keyboard-selectable draft and explains copying; session-change cleanup never lets a new identity copy old text. Independent contact links contain no report payload or identity parameters.
9. After acknowledged D1 acceptance, close browser, deactivate WordPress plugin and rotate its credential. Service delivery/reconciliation proceeds independently subject to safety/suppression; pending deadline is 24 hours, while unknown stays unknown and triggers review. An empty marker scan never causes another GitHub create.
10. Block/mispackage/hang app scripts and CSS: loader leaves other admin controls usable, stops after its 10-second total attempt budget, provides explicit retry and usable server-rendered contact; late assets cannot mount a second panel. No automatic retry or support health probe.
11. Enable the implemented fail-safe: zero support outbound HTTP from submission, reads, enrollment or setup status; no widget assets; authenticated sanitized unavailable response; normal pages and other plugins still work. Deactivation performs no remote erase/revoke or expensive site loop and schedules no report jobs.
12. Production readiness drill: authorized Reporter retrieves the verified contract contact without WordPress or support Worker; Operator receives a manually described uncertain submission, reconciles it without blind recreation, and records sanitized evidence. Gate production data collection on this drill plus [Make delivery erasure and retention safe under unknown outcomes](https://github.com/Quick-Release/gq-support/issues/46)'s privacy requirements.

No production code, persistent draft storage, local queue, new provider or automatic message delivery is introduced by this research.
